# ticket-build

Turn `.dev/plans/<KEY>.md` into working, tested code on a properly named GitLab branch. Optimize for "it works and the tests prove it" — deep critique is the next phase's job, done in fresh context, so don't try to review your own work here.

## Why hold back on self-review

You wrote this code and you're invested in it, so your own review will share its blind spots. Get it working and green, then hand a clean diff to `ticket-review` (ideally a fresh conversation). Trying to do both at once produces mediocre code and a shallow review.

## Steps

0. **Pick the mode.** Check both findings ledgers — `.dev/reviews/<KEY>.md` (subagent review, IDs `B*`/`S*`/`N*`) and `.dev/mr-comments/<KEY>.md` (human MR reviewer comments, IDs `H*`, written by `ticket-feedback`):
   - If either exists and has findings without a `Resolution:` line → **fix mode**: your work list is those findings — the review's Blocking (and, if the user wants, Should-fix) findings, plus whichever `H*` numbers the user picked — not the plan's tasks. If both files have open findings, ask which set to work rather than merging them silently. Stay on the existing branch. Work one finding per approval cycle — never chain fixes or commits automatically. For each finding: fix it, run the relevant tests, **prove every new or changed assertion bites (step 3)**, then **present the change for review and stop at the approval gate** — show the diff (or a tight summary) and the test result, and **ask for explicit approval before committing.** Only on approval: commit with the key (`PROJ-123: fix — <finding summary>`) and append `Resolution: fixed <commit-sha>` under the finding **in the file it came from** — both ledgers are local and uncommitted, so the append never enters a commit. If the user asks for changes, rework and re-present; if they tell you to stop pausing (e.g. "just fix the rest"), you may proceed unattended from that point. If the user decides a finding won't be fixed, record `Resolution: waived — <reason>` instead; never waive silently on your own. If a finding turns out to need a product decision only the user can make, record `Resolution: escalated — <the question, and who owns it>` and treat it as still open rather than leaving the line blank, which reads identically to "ignored".

     **An `H*` finding's "Proposed fix" is a proposal, not an instruction.** Verify it against the code before implementing it, the same way you would a plan task, and if it turns out to be wrong or to have gone stale since it was written, say so and stop rather than implementing it faithfully. It also carries a `plan-impact:` line: when that is anything but `none`, the plan edit named there is part of this finding's approval cycle, not a follow-up.

     **Fix mode is not exempt from step 4.** A fix that deviates from the plan's design updates the plan in the same approval cycle — the mechanism it now uses, the assumption it invalidates, the task list, the verification status. Fix mode feels like "just addressing findings", which is exactly why this gets skipped: a re-review can find the plan stale in half a dozen places, every divergence introduced by a fix that deliberately departed from it. The merge request description gets written from the plan, so a stale plan ships as a wrong MR description. Two specific traps to check for while you are in here: a fix written to close a blind-test finding is a prime site for a *new* blind test, and a test that asserts on a side channel (a log line, a metric, an emitted event) must assert its **content**, not merely that it fired — pinning only which channel or severity was used leaves the payload, which is usually the entire deliverable, free to change to anything.
   - Otherwise → **build mode**, steps below.

1. **Load the plan.** Read `.dev/plans/<KEY>.md`. If it's missing, stop and tell the user to run `ticket-plan` first — building without a plan is how the phase separation collapses. Skim the Jira ticket again (`Atlassian:getJiraIssue`) before starting: if acceptance criteria changed since planning, flag it and update the plan rather than building against a stale contract.

2. **Branch.** Create a single branch for the whole ticket, named after the Jira key alone (e.g. `PROJ-123`) — the key is the entire branch name, no description suffix. One branch per ticket, one commit per task — never a branch per task; task-level granularity lives in the commit history, which GitLab's MR UI can review commit-by-commit. The key in the branch name is what makes GitLab↔Jira linking free, so always include it.

   Before the first commit, confirm `.dev/` is git-excluded: `git check-ignore -q .dev`, and if it doesn't match, append `.dev/` to `.git/info/exclude` under a `# ticket-flow workflow artifacts (local only)` comment. `ticket-plan` normally did this already, but this phase can be entered directly with an inline plan, and one unexcluded commit is enough to put the plan in the team's history.

3. **Work task by task, in plan order — one task per approval cycle.** Do one task, then stop for the user; never chain tasks or commits automatically. For each task:
   - Implement the smallest slice that satisfies it.
   - Write or adjust the tests the plan called for, alongside the code — not at the end. If the plan contains a standalone "write the tests" task, that is a planning bug: fold its tests into the tasks they cover and note the drift.
   - Run the project's test command — the plan names it — scoped as narrowly as still covers the change, and confirm green. A branch that's green after every task is trivial to bisect and review; one that's only green at the end hides which change broke what.
     **Confirm green from the runner's exit status, not from the tail of its output.** Piping through `| tail` or `| grep` reports the *filter's* status, which is almost always success — that has already turned a failed suite into a reported "exit code 0". And after any mutation experiment, force a fresh run rather than accepting an incremental one — most runners have a flag for it, and the plan's test strategy is the place to record which. Restoring the file you mutated can drop the build back onto a cached result, so the green you are reading may predate your change entirely.
   - **If a task's tests cannot run because the environment is unavailable** — no Docker daemon, no licence, no device, no network — do not commit the task and do not present it as green. Say which criteria are unproven and what has to be running, hold the task at the approval gate, and ask the user to bring the environment up rather than starting it for them. Writing the code is not the deliverable; the evidence is.
   - **Prove each new test bites — per assertion, not per task.** A green test says nothing until you have seen it fail: revert the production change, watch it fail, restore, watch it pass — then report that you did. Do this for **each** new test against **the specific production line that test claims to cover**. A task-level revert that reddens some test says nothing about the others: two tests that could not fail for the reason they existed shipped through exactly that check, because reverting the feature reddened the feature's tests and nobody mutated the one line each of the others was written to guard. If a test's target line cannot be isolated, that is itself the signal that the test is bound to a mock rather than to behaviour.
     A *characterization* test of existing behaviour passes either way; say so explicitly rather than letting it read as a regression guard. Watch for the tautology, where the fixture establishes the very relationship the assertion checks — that proves only that the language works.
   - **Where the thing under test *is* how a collaborator behaves, use a real fixture, not a mock.** Filesystem naming, path semantics, a driver's return contract: mock those and the test asserts your assumption about the collaborator instead of the collaborator's actual behaviour, so it stays green precisely when the assumption is wrong. Check whether the repo already encodes this split — a naming suffix, a separate directory or source set — and follow it.
   - **If you verify something with a throwaway harness, promote it or record it.** Some code has no harness in the repo — build scripts, launcher glue, shell invocation — and a scratch script beats reasoning alone. But scratch output dies with the session, leaving the next reader with untested code. Either promote it to a real test or paste the script and its output into the plan under the task; untested glue is exactly where platform-specific bugs survive review.
   - **Green tests are not proof the project builds.** Many test runners type-check more loosely than the real build, or compile only a subset of the sources, so a passing suite can sit on top of code that fails to compile for shipping. Before presenting a task, also run whatever command actually builds or compiles what you touched — and if the project has several build targets or config roots, the one covering your files. Find that command once, from the project's own docs or scripts, and record it in the plan's test strategy so later tasks don't rediscover it the hard way. "Tests pass" and "it compiles" are two claims; only report the one you ran.
   - **Present the task for review and stop at the approval gate.** Show the user what this task changed — the diff (or a tight summary of it) and the test result — name which task it was and what remains, then **ask for explicit approval before committing.** Do not commit and do not start the next task until the user approves. If they ask for changes, rework this task and re-present it; only a clear go-ahead ("approved", "looks good", "commit it", "next") clears the gate. If the user tells you to stop pausing (e.g. "just finish the rest"), you may proceed unattended from that point — but only on that explicit instruction; the default is one task per approval.
   - **On approval, commit and tick.** Stage the concrete files this task touched — never `git add -A`, `git add .`, or `git commit -a`; a blanket add sweeps in unrelated work and is the one habit that would drag `.dev/` into history if the exclude entry were ever missing. Commit with the Jira key in the message, e.g. `PROJ-123: add retry backoff to client` — one commit per task, the granularity reviewers and `git bisect` will lean on — then tick the task in the plan file (`[ ]` → `[x]`). The tick happens after the commit, which is harmless precisely because the plan file is untracked; it never trails into the next task's diff. If a task is genuinely half of an inseparable pair (interface now, implementation next task) and greening it would mean writing throwaway stubs, it's acceptable to commit red **once**, marked `WIP` with the reason in the commit message — but the very next commit must restore green.

     **Prefer merging over a red commit.** If two tasks cannot be split without leaving the tree incoherent — worse, in a transient version of the bug being fixed — make them one task and one commit, recorded as drift. Task boundaries are a forecast, not a contract.

     **If the user commits instead of you**, confirm what actually landed (`git show --stat HEAD`) before ticking the plan, rather than assuming your proposed message and file list were used. Check too that the subject describes what actually landed: a commit titled for tests while carrying a production change misleads anyone reviewing commit-by-commit, and a subject with leading whitespace or a missing key breaks the GitLab↔Jira link. Before handing off, check the branch for message consistency (`git log --oneline <base>..HEAD`). If a misleading commit is already pushed, don't rewrite published history — note it for the MR description instead.

4. **Handle plan drift honestly.** If reality contradicts the plan (a task turns out unnecessary, a new one is needed, an assumption was wrong), update the plan file to match what you actually did and note it. A stale plan makes the review phase useless. The no-assumptions rule from planning carries over: if you hit an ambiguity the plan and its Clarifications don't cover, stop and ask the user, record the answer in the plan's Clarifications section, then continue — don't pick an interpretation just to keep momentum.

5. **Watch the things that bit before.** Don't hardcode secrets or credentials into config/ConfigMaps — use the project's secret mechanism. Clean up resources, handle the error paths the plan flagged.

6. **Close the verification gate before claiming the ticket is done.** Fill in the plan's **Verification status** from what you actually observed: for each *demonstrable-by-test* criterion name the test or command you ran; each *requires-manual-run* criterion is **not done** until a human executes it, and you cannot close those yourself.

   If any manual criterion is unexecuted, do not report the ticket as complete — say which criteria are unproven, give the exact steps, and treat the branch as blocked on them. "All tasks committed and the suite is green" is a different claim from "the ticket's problem is fixed". Where the criterion the whole ticket exists for is manual, lead with that rather than burying it under what you did prove.

## Boundaries

Don't open the MR or transition the Jira status here. Never stage, commit, or `git add -f` anything under `.dev/` — the plan and review files are local scratch, and the commits on this branch should contain code and tests only. When the branch is green, every task is done and the verification gate is closed, summarize what you built and any deviations from the plan, then point the user at `ticket-review` — and suggest they run it in a fresh conversation so the reviewer isn't anchored by everything above.

**After a fix-mode pass, send it back for re-review.** Fixing several findings at once — especially across different layers — is itself a substantial change, written by the same agent that wrote the original. Re-run `ticket-review` scoped to the fix commits plus anything marked waived. The larger the fix batch, the less optional this is.
